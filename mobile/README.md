# YenTool 手機版 PWA

把掃描結果與**自己的真實持倉**做成可安裝到 iPhone 主畫面的網頁 App。
不需要 Xcode、不需要 Apple 開發者帳號、不需要上架審核。

## 這個 App 回答五個問題（報告 7.1）

| 頁面 | 回答什麼 |
|---|---|
| 今日總覽 | 今天要注意什麼？資料日期、四種總損益、待處理清單 |
| 今日建議 | 哪些是新的有效建議？固定首日價、有效期限、不可買的原因 |
| 我的持倉 | 我實際買了什麼、現在賺賠多少、有效賣出計畫是什麼 |
| 績效與歷史 | 十日成果、已實現／未實現、已平倉、建議與實際的差異 |
| 研究與資料狀態 | 為什麼選它、數據可不可信、內建計算自我檢查 |

## 檔案

| 檔案 | 用途 |
|---|---|
| `index.html` | 外殼：頁首、五個頁面容器、底部分頁列 |
| `app.js` | 全部前端邏輯（帳本、估值、畫面、表單）。無框架、無建置步驟、無 CDN |
| `styles.css` | 樣式。375 / 390 / 430px 手機優先 |
| `sw.js` | Service Worker，離線快取（僅 https / localhost 生效） |
| `manifest.webmanifest` / `icons/` | 加到主畫面用 |
| `scan_result.json` | 掃描結果（由 `scanner/result_export.py` 產生） |
| `quotes.json` | 收盤價視窗（由 `scanner/quote_feed.py` 產生） |
| `serve.py` | 本機測試用的小型伺服器 |

## 資料怎麼來

> **這兩個檔案不在版本庫裡**（2026-09-20 起）。它們由每次掃描產生，直接上傳到
> GitHub Pages；版本庫留一份的結果是那份檔案停在 2026-07，欄位契約有 21 項錯誤，
> 而且行情抓不到那一輪還會被當成「今天的結果」發布到手機。
> 本機要測畫面時自己抓一份現成的：
>
> ```bash
> curl -o mobile/scan_result.json https://luke820001.github.io/yentool/scan_result.json
> curl -o mobile/quotes.json      https://luke820001.github.io/yentool/quotes.json
> python mobile/serve.py
> ```

掃描器每次跑完會同時寫兩個檔到這個資料夾：

* **`scan_result.json`** = `{meta, rows}`。`meta` 帶模式、策略版本、掃描時間、
  行情日期、`calendar_tail`（真實交易日）、`regime`（大盤判定，含 `as_of_date`
  與 `is_current`）、`market_leg`（`{日期: true|false}`：該日加權指數收盤低於 20 日均線、仍高於 60 日均線，
  用來決定第 10 天之後是否因大盤續抱；沒有的日期＝未知＝視為關閉，與後端重放相同，
  整個欄位缺少時手機只看個股自己的 5 日均線）、`quality`、`degraded`、`reports`（AI 報告，`{市場: 文字}`）、
  `report_sources`（每份報告的來源 `{市場: {source, model, attempts, seconds, error}}`，
  `source` 為 `gemini` / `groq` / `template`；`template` 表示 AI 沒有回應、
  內容是本機依規則產生的模板，畫面應標示「模板·非 AI」。舊檔沒有這個欄位時，
  以報告第一行是否為【模板報告 / 【本地報告 判斷）。
  每個 `row` 帶技術欄位，以及**後端算好的買進判定** `Buy_Ready` / `Buy_Block`，
  和**固定首日建議** `Recommendation_ID` / `Initial_Buy_Price` /
  `Recommended_On` / `Rec_Status` / `Rec_Valid_Until`。
* **`quotes.json`** = `{as_of, sessions[], closes{}, names{}, price_basis, missing[]}`，
  最近 30 個交易日的收盤價，涵蓋**整個市場**（約 1,900 檔），不是只有掃描名單。
  這是刻意的隱私設計：這個檔案是公開的，如果它只放「名單 ∪ 你的持倉」，那麼一檔
  出現在檔案裡、卻不在當天名單上的股票，就只可能是因為有人持有它 —— 等於公告持股。
  全部都放進去，「出現在檔案裡」就不帶任何訊息。

### 兩條鐵則

1. **買進資格由後端決定。** 這個 App 只讀 `Buy_Ready` / `Buy_Block`，不自己重算
   規則。它唯一被允許做的事是「降級」——資料日期過舊、建議過期、大盤判定不是最新，
   都會把「可買」降成「需重新確認」。它**永遠不會**把後端的拒絕改成可買；
   後端沒給判定（舊版 JSON）也一律當成不可買。
2. **持倉估值一律取自 `quotes.json`，不從掃描列取價。** 買進之後掉出名單是正常的，
   掉出名單不代表停止估值。

## 我的持倉：一本真的帳（報告 5、6、9.1）

持倉存在手機的 **IndexedDB**（`yentool_ledger`），四個 object store：

| store | key | 內容 |
|---|---|---|
| `positions` | `position_id` | 一檔持倉的容器。所有金額欄位都是**推導出來的**，不可直接寫 |
| `executions` | `execution_id` | 唯一的事實來源。只增不改：更正＝寫新版本並把舊筆標為非現行；撤銷＝標記作廢但保留 |
| `marks` | `[position_id, session_date]` | 每個交易日的收盤、股數、成本、四種總損益、當日損益 |
| `meta` | `key` | 設定、遷移旗標，以及凍結的十日成果（`cycle:<持倉>:<天期>:position`） |

* **成本法**：移動加權平均。`cost_basis` 含買入手續費，`gross_cost` 不含。
* **已實現淨損益** ＝ 賣出金額 − 手續費 − 交易稅 − 該次移除的帳面成本。
* **費稅**：買賣各 0.1425%、賣出稅 0.3%，最低 20 元、元位無條件捨去（可在研究頁切換
  成未取整版本）。費率是**版本化資料**，不是常數；每筆成交都記下當時的費率版本。
* **金額全部用整數「分」計算**，不用浮點數。差 30 分不會因為 `0.1+0.2 !== 0.3`
  而變成賺或賠（報告 9.1）。
* **當日損益 ＝ 當日累計 − 前一日累計**，絕不把每日累計值相加。報告 6.2 的例子
  相加會得到 45,000，正確答案是 10,000。研究頁的「自我檢查」每次開啟都在你的手機上
  實跑一次這個例子。
* **第 10 個交易日的成果會被凍結**，之後的價格不會改寫它。若第 11 天仍持有，
  部位繼續估值，同時出現在「待處理」。

### 四種總損益不共用同一個標題（報告 6.3）

| 名稱 | 意思 |
|---|---|
| 價差總損益 | 只算價差，不含任何費稅 |
| 帳面總損益 | 已實現淨損益 ＋ 未實現帳面損益 ＋ 已認列配息 |
| 若今日全數賣出估計淨損益 | 帳面總損益 − 剩餘持股的預估賣出費稅 |
| 已實現淨損益 | 真的入袋、已扣費稅的部分 |

報酬率有兩個分母，也不共用標題：**相對首日建議價**（固定的 `Initial_Buy_Price`）
與**相對實際成本**（你的平均成本）。報告 6.2 的例子兩者分別是 +12% 與 +9.80%。

### 移除持倉有三個不同的動作（報告 7.4）

* **登錄賣出** —— 記一筆真實賣出成交，可部分賣出。股數歸零才算平倉。
* **封存已結束紀錄** —— 已平倉的部位從工作清單收起來，資料保留在「績效與歷史」，
  已實現損益仍計入帳戶總額。**封存後仍然可以改**：在「績效與歷史」的那一列按
  「更正」就會開啟同一份成交明細，可以修改成交價、股數、日期，或撤銷誤登，
  舊版本一律保留。若更正之後這筆又有持股（例如撤銷了結清的賣出），它會自動
  移回「持倉」並提示你，不會變成一筆看不見卻仍在計算的部位。
* **撤銷誤登** —— 這筆根本不該存在。標記作廢、不再計入損益，但**紀錄保留**。
* **刪除這筆紀錄** —— 真的拿掉，持倉頁與「績效與歷史」都有。
  連同成交、估值列與凍結的十日成果一起消失，**無法復原**。
  確認視窗會先告訴你會少掉幾筆成交與多少已實現損益。
  登錄了又撤銷、完全沒有有效成交的那種紀錄，現在可以直接清掉，
  不再卡在持倉清單上說自己「持有中」。

## 備份：資料只在這支手機上

持倉與成交**只存在這台裝置的瀏覽器**。清除瀏覽器資料、換手機、重灌都會消失，
而且它不會、也不應該被上傳到公開的 GitHub Pages（報告 9.2）。

* 「持倉」或「研究」頁 → **匯出備份 JSON**。
  **這個檔案是未加密的明文**，裡面有每一筆成交價、股數與日期。它只會存到你裝置的
  下載資料夾，不會經過網路 —— 但如果你把它放進共用的雲端硬碟、或用通訊軟體傳送，
  持倉資料就離開你的裝置了。要備份請放在只有你能存取的地方。
* 還原用 **匯入備份**。匯入會驗證股號、股數、價格與日期格式，格式不符會拒絕。

第一次開啟時，舊版 `localStorage`（`yt_holdings_v1`）的持倉會自動搬進新帳本。
**舊格式沒有股數**，所以搬過來的每一筆都標成「待補股數」並要求你補登實際成交——
系統不會替你猜一個數量（報告 11.5）。舊資料本身會原封不動留在 `meta` 裡。

## 在 iPhone 安裝（同一個 Wi-Fi）

1. 電腦上跑 `python mobile/serve.py`，會印出 `http://192.168.x.x:8000/`。
2. iPhone 用 **Safari** 打開該網址。
3. 分享鈕 → **加入主畫面**。

> 區網 http 不會啟用 Service Worker（需要 https），所以離線快取不生效，
> 但 App 本身可正常使用。要真正離線就把整個 `mobile/` 放到任何 https 靜態空間。

## 離線與快取

Service Worker 走 network-first：有網路一定看到最新的掃描與最新的版本，
快取只是斷線時的退路。**快取鍵一律是去掉 query 的網址**，所以 `?v=12`、
`?t=…` 這類參數不會把同一個檔案切成好幾份（這正是舊版離線讀不到資料、
快取又每次開 App 就多一筆死資料的原因）。版本升級時舊快取會整個刪掉。

## 名詞（報告第 8 節）

畫面上的名稱刻意講清楚它到底是什麼：

* 現價 → **最新收盤價**（旁邊一定有資料日期）
* 進場參考 → 拆成**首日建議價**（固定）與**最新觀察參考**（每次重算，不是新指令）
* `Risk_Pct` → **停損距離%**（不是虧損機率）
* `ATR_Pct` → **20日平均日振幅%**（不含前收跳空，不是標準 ATR）
* `Donchian_Break` → **通道上緣接近**（不一定真的突破）
* `Volume_Dryup` → **近3日均量／20日均量**
* `Dist_52W_High` → **距近一年最高收盤**
* `Launch/Surge/Explosion_Score` → **起漲條件分／動能分／盤整蓄勢分**，都是規則分數
* 停利、鎖利價是**條件**，不是已達成的狀態；畫面不會把門檻數字寫成承諾
* 盈虧不只靠紅綠：一定同時有正負號和「獲利／虧損／持平」的字

## 「帳本實際」（2026-09-23）

策略卡展開後，回測數字下面多了三行「帳本實際」：掃描器從 2026-06-25 起**真的發出過**的
首日、上櫃、前 20 名訊號，按買進規則分成「符合完整買進規則」「名單上但不可買」
「核心+ 但大盤未順風」三桶，各自用完整出場規則（隔日開盤進、含費稅、續抱到 20 天）重放後
的筆數、勝率、平均與合計。後端 `scanner/live_record.py` 每次掃描重算，放在 `meta.live_record`；
桌面掃描沒有重算時會沿用上一次的並標示「沿用上一次掃描算的」。

## 建議頁三組、資金與下單指引（2026-10-08，v31）

建議頁分成「今日可買」、「模擬持有中（今天動作）」和「參考」三組。分組只看後端欄位
（`Buy_Ready`／`Buy_Block`、`Hold_Status`、`Exit_Signal`），手機只會把「可買」降級，不會升級。

- **股數與費用**：資金、檔數（預設 8）和每筆風險 % 存在 IndexedDB 的 meta `sizing`
  （`{capital_cents, max_slots, risk_pct}`，和費率設定放在一起），所以會跟著「匯出備份」一起帶走，
  匯入時也會檢查範圍。另外在 `localStorage` 的 `yt_sizing_v1` 存一份備用。
  讀寫都包了 try/catch，瀏覽器不允許儲存時，這次開啟仍可使用，只是不會記住。費稅算法與 `portfolio/money.py` 相同：
  手續費取到元、最低 NT$20；證交稅取到元。
- **下單指引**：交易規則（零股 09:10 起撮合等）寫在 `app.js` 的 `ORDER_RULES`，附查核日期。
  處置與注意股的撮合分鐘數和預收款只取自後端的 `Restriction_Match_Min`、`Restriction_Prepay`，
  不寫死在手機端。
- **績效頁**的「系統訊號紀錄」直接讀 `meta.live_record`（tradable、bench、by_restriction、by_sid），不是帳本。
  出場原因表、曲線和「排除起始日批次」是用 `tradable.trades` 算的；後端只保留最近 40 筆
  （`live_record.TRADES_KEPT`），超過時畫面會標明「只就保留的最近 N 筆計算」，標題那一行才是全部筆數。
- **驗證**：`node tests/mobile_probe.js` 在 node vm 裡啟動整個 `app.js`，用三份資料各畫一次每一頁，
  分別是 `tests/fixtures/mobile/scan_2026-09-23.json`（09-23 舊版資料，沒有新欄位）、
  `tests/fixtures/mobile/scan_2026-10-07.json`，以及一份合成的新欄位資料。`mobile/scan_result.json` 不進 git，
  測試不讀它。`tests/test_mobile_probe.py` 另外用 `portfolio/money.py` 產生約 5,800 筆手續費／證交稅格點，
  以 `--fee-grid` 交給 probe 逐筆比對；沒有安裝 node 時跳過。

## 已結案建議的完整紀錄（2026-10-09，v33）

績效頁在「系統訊號紀錄」下面，列出每一筆已結案的建議（最近 20 筆，新的在前），順序固定是：
訊號日 → 規則進場日與開盤價 → 出場判定日 → 出場成交日、價格與價格依據 → 出場原因 → 持有幾個交易日／日曆天
→ 毛報酬、淨報酬、成本 → 最高（MFE）與最低（MAE）。期滿出場另列一行「實盤：當晚下單，隔日開盤 … 約 …」，
因為帳上記的是收盤價，實盤要到隔日開盤才賣得到。「逐日明細」可展開，每個持有的交易日一列。
手機只顯示後端存下的紀錄，不重算、不改寫；紀錄自己對不上（天數與路徑筆數不同、毛報酬與進出場價不符等）時會標出來，數字仍照原樣。

- **資料來源**：`recommendations.json`（後端 `data/recommendations.json` 的公開匯出），只在開績效頁時讀一次，
  不帶任何參數。這支手機目前只部署 `mobile/`，所以發布流程要把這個檔放進去；沒有時畫面顯示
  「這次部署沒有 recommendations.json」，其他頁不受影響。Service Worker 與 scan_result.json 一樣 network-first。
- **`outcome` 合約**：每筆建議的 `outcome` 是物件，有些匯出是 JSON 文字，兩種都讀。
  `record_schema` 1 的完整紀錄有 `signal_session`、`planned_entry_session`、`entry_date`、`entry_price`、
  `exit_decision_date`、`exit_fill_date`、`exit_price`、`exit_basis`（`level` 盤中觸價／`open` 開盤跳空或隔日開盤賣／`close` 收盤價）、
  `reason`、`bars`、`calendar_days`、`ret_gross_pct`、`ret_net_pct`、`cost_pct`、`mfe_pct`、`mae_pct`、
  `live_fill_date`、`live_fill_price`（只有期滿出場有）和 `path`。後期收下的判定日是成交日的前一個交易日。
  `path` 每列是 `{date, open, high, low, close, close_ret_pct, status, stop, day, ride}`，
  `status` 是 `holding`、`armed`、`sell_next_open` 或 `exit_<原因>`，`ride` 為真表示第 10 天之後續抱。
- **舊紀錄**：沒有 `record_schema`、`path` 的只有八個摘要鍵，顯示成摘要並註明「早期紀錄，沒有逐日路徑」；
  缺的數字一律是破折號，不會變成 NaN、undefined 或 0。`path` 不是清單、是空的或有壞列時，各自有說明，壞列略過並計數。
- **對帳**：這筆建議如果有你登錄的成交（持倉的 `recommendation_id` 對到這筆建議，已撤銷的不算），
  就多一塊「你的成交 vs 規則」：買進比規則晚幾個交易日、價差百分比；賣出日與價格對規則的出場成交
  （期滿出場另對照隔日開盤的實盤價）；你的淨報酬對規則淨報酬差幾個百分點。沒有成交就什麼都不多顯示。
  你的成交只存在這支手機的 IndexedDB：只在畫面上比較，不送出、不寫檔、不寫回帳本，也沒有任何請求帶著它。

  JSON 文字、壞資料、對帳算術）逐行比對畫面；P 節（`--trade-grid`）由 `tests/test_mobile_trade_record.py`
  用真正的 `replay_trade` 與 `trade_record` 現場產生紀錄，再與手機畫出的數字比對。
