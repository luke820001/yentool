# Pinned resolution for CI, so the daily scan installs the same packages today
# and next month. requirements.txt keeps the ranges that describe what the code
# SUPPORTS; this file records the one resolution that has actually been tested.
#
# Why it exists (2026-09-20 audit, AUD-006): both workflows ran
# `pip install -r requirements.txt` against ranges as wide as
# `yfinance>=0.2.0,<2.0.0`, so every run resolved whatever was newest that
# morning. On 2026-09-20 CI installed yfinance 1.7.0 while this project's own
# machine had 1.4.1 -- and yfinance is the dependency that decides what a price
# bar even is. A feed library silently changing under a scheduled job that
# writes stops for real positions is not a risk worth taking for the
# convenience of automatic upgrades.
#
# These versions are the set CI resolved and the full suite passed on
# (Python 3.12.14, run 35514607808).
#
# To upgrade: edit a version here, push, and let the tests workflow prove it.
# Keep this in sync with requirements.txt's supported ranges -- a pin outside
# its range will fail to install, which is the intended way to find out.
#
# Not hashed yet: hashes need pip-tools or uv, which this project does not
# install. Version pinning removes the day-to-day drift; hashes would add
# tamper evidence, and are the next step if this ever builds on a shared
# runner that is not GitHub's.
