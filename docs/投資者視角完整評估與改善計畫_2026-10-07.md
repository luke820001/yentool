### 2.1 唯一的「可買」：8227 巨有科技 @372

事實鏈（全部有資料可對）：

| 日期 | 事件 | 系統狀態 |
|---|---|---|
| 09-16 | 首次進榜（rank 16，收 272） | block=regime（當天大盤門檻未開） |
| 09-17 | 走勢重播視為「隔日開盤進場 @≈272.5」 | 之後 lock 上鎖，Plan_Stop 278 |
| 09-18 ~ 09-23 | 榜上，rank 11–18 | block=quality（非 CORE+） |
| 09-24 ~ 09-30 | 榜上，rank 23–37 | block=rank |
| 09-29 | 重播判定 **tp 出場 @327.6（第 7 天）** | 卡片：「⚠ 達到目標·出場」 |
| 09-30 | **漲停鎖死** 370.5 | 榜上 rank 37 |
| 10-01 | **爆量 16 倍、反轉** | 掉出榜（成交量崩） |
| 10-02 ~ 10-08 | **TPEX 公告處置股**（五分鐘撮合、預收款） | 系統完全不知道 |
| 10-01 ~ 10-06 | 不在榜（4 個交易日） | — |
| 10-07 | 重新進榜 rank 5，CORE+ 成立 | **First_Day=True → fresh → Buy_Ready** |

為什麼會這樣（機制，不是巧合）：

1. `mark_buy_ready` 的 `fresh = pending | (First_Day & known)`。First_Day 只看「前一個 ledger session 不在榜」，
   不看走勢重播的結論。8227 的重播狀態是 **exited(tp)**，但因為中間缺席 4 天，First_Day 又是 True，於是「已出場」+「首日」= 可買。
   建議檔的 `gate_snapshot` 自己就記錄了 `Hold_Status: "exited"` 與 `Buy_Ready: true` 並存。
2. `holding_tracker._streak_start(gap_tol=10)` 把 ≤10 天的缺席視為同一段，所以卡片仍帶著 09-17 那段的
   Entry_Date / Hold_Day=7 / Plan_Stop=278 / Exit_Signal=tp；而建議檔另外算了 372 的新停損 297.5 與停利 446.5。
   手機卡片把兩套混在一起顯示：停損 278、停利 446.5。
3. 掃描器沒有任何「處置股 / 注意股 / 漲停鎖死 / 爆量反轉」的欄位。CORE+ 看的是距 52 週高 ≤5%、5 日漲幅 ≤5%、ATR ≥4.5，
   一檔剛爆量反轉後橫盤兩天的股票，剛好同時滿足三項。

投資者實際會遇到的事：10/08 掛「開盤市價」不會成交（處置股改為每 5 分鐘集合競購，且需預收款）；
就算成交，也是在一段六週 +125% 的末端、剛出現量能高潮反轉的位置建倉，停損 −20% 等於 −74 元。

## 3. 建議的時間點為什麼怪

### 3.1 設計上的時間線（文件寫的）

`scan-timer.yml` 15:00 台北時間觸發 → 掃描 → 約 15:06 發布 → 投資者看到 → **隔日開盤**進場（規則 next-open）。
這條線本身是合理的：收盤資料、當晚決策、隔日執行。

### 3.2 實際發生的時間線（ledger 寫的）

最近 25 個交易日的 `picks.scan_ts`：

- **只有今天 10-07 是 15:05 寫入**；其餘 24 天全是 **22:03 ~ 00:12** 寫入。
- 原因：`scan.yml` 的備援 cron（約 21:00–00:40 台北）照樣執行，而同日重跑會 **刪掉當天的 picks 再重寫**，
  建議檔也會重新 attach。今天看到 15:05 是因為晚上的 cron 還沒跑。
- 所以：投資者 15:06 看到的清單、23:00 被覆寫的清單、隔天早上開盤前打開手機看到的清單，**可能是三個版本**。
  4 筆建議的建立時間分別是 22:20、22:49、23:37、15:05，就是證據。

### 3.3 首次發布可能是「降級版」

10-05 15:15 OTC feed 0 列 → 發布了一份只有上市 37 列的清單（紅色 banner），80 分鐘後才被完整版取代。
投資者在 15:06 看到的是「今天沒有任何上櫃股」。
09-17 則是反過來：晚上 TSE 0 列的降級跑產生了 5274 的建議（§2.3）。

### 3.4 「隔日開盤」對不上台股的執行現實

- 處置股：五分鐘集合競價、部分券商要求預收款，市價單不適用（8227、6533 今天就是）。
- 漲停鎖死日：收盤價 = 漲停價且量縮，隔日開盤大概率跳空，next-open 成交價與回測假設偏離（8227 09-30）。
- 零股：盤中零股撮合每 1 分鐘一次、開盤 09:10 才開始，與「09:00 開盤價」不是同一個價格；
  本機 `money.py` 已有 NT$20 最低手續費，但畫面不顯示「這筆建議以你的資金買幾股、手續費吃掉幾 %」。

### 3.5 06-25 的 5 筆同日訊號

live_record 的 11 筆訊號裡 5 筆是 06-25（ledger 起始日，所有當天在榜的名字都被當成「首日」）。
這讓戰績表看起來「以前一天 5 檔、現在一個月 1 檔」，其實是起點假象，但沒人在畫面上說明。

## 4. 為什麼標的這麼少

### 4.1 每日漏斗（ledger 最近 25 個交易日）

|---|---|
| 成交金額前 300（≥ 0.5 億） | 300 |
| Launch_Score 前 20 + 滯後保留 | 40–47 列 |
| 前 20 之中的上櫃 | 2–7 |
| 其中 CORE+ | 0–3 |
| 其中 fresh（首日 / pending） | 0–1 |
| **Buy_Ready** | 9 月全月 1 檔（1815）、10 月至今 2 檔（3498、8227） |

### 4.2 哪些是設計（已驗證，不該放寬）

- 上櫃限定、CORE+ 門檻、regime 門檻、hold 10：BACKTEST_LOG J / J.5 / L 已逐一測過放寬方案並拒絕
  （放寬會把 70.8% 拉回 50% 區間）。STRATEGY §3.7 的拒絕清單不重提。
- 研究結論 K：獲利集中在 17% 的 tp 單，time 出場平均 −9.9%，**倉位數（slots）決定年化 9%→36%**。
  也就是說「少」是這個策略的本質：它靠少數大贏，需要的是「每次都接得住」而不是「更多檔」。

### 4.3 哪些是 bug / 不一致（可以修）

- `project_backtest_round2`：**線上掃描器只發出驗證規則 54% 的訊號**。研究 harness 與線上 `mark_buy_ready` 的
  「訊號日」定義不同（First_Day vs 研究端的首次符合日 + 冷卻），漏掉一半、又多出 8227/3498 這種假首日。
- rank<20 在 J.6 已證明是 no-op（CORE+ 已經更嚴），但 N_ENTER 是真實軸，尚未在線上與研究端對齊。
- 降級跑、晚間覆寫、永不過期，讓「少」還帶著「錯」：少不可怕，少又錯才致命。

## 6. 改善計畫

原則：先把「假訊號」與「時間線」修到投資者能信任，再補資訊，最後才做研究。
不碰：出場規則參數、CORE+/上櫃門檻、PC 端排程、手機 token 流程。

### P0 — 不修就不能照做（目標：一週內）

| # | 項目 | 做法 | 驗收 |
|---|---|---|---|
| P0-1 | **處置股 / 注意股 / 漲停鎖死 封鎖** | 每日掃描前抓 TPEX 處置清單 + TWSE 注意/處置清單（已確認可用的端點），新增 `Trade_Restriction` 欄（disposition / attention / limit_lock）；`mark_buy_ready` 新增 block=`restricted`；建議檔不得對受限股建立；卡片顯示紅色標籤與期間 | 10-07 的 8227、6533 必須 block；`result_checks` 新增 `restricted_buy_ready` 錯誤級檢查 |
| P0-2 | **fresh 與走勢重播對齊** | `fresh` 不得只看 First_Day；若 `Hold_Status in (exited, …)` 且距重播出場 < hold(10) 個交易日，block=`cooldown`；研究 harness 用相同定義重新數訊號 | 線上/研究訊號一致率從 54% → ≥ 90%（以 06-25 起重算）；8227、3498 兩例在回放中不再 Buy_Ready |
| P0-3 | **降級跑不得產生或修改建議** | `scan_headless` 的 degraded 分支跳過 `attach_recommendations`，且不覆寫 ledger picks | 回放 09-17：rec-5274 不會被建立 |

| P0-5 | **當日清單凍結，晚間備援只補不改** | 15:06 成功發布後，同日重跑只允許更新 outcomes / quotes / tracked，不重寫 picks 與建議；備援 cron 僅在當日尚無 `published_today` 時才產生清單 | ledger 每日 `scan_ts` 保持 15:0x；手機「掃描時間」整晚不變 |
