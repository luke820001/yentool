# 排程準時與盤中行情

> 2026-09-10 實測調查。所有數字都是量出來的,不是查文件推測的。

## 一、排程為什麼不準

`.github/workflows/scan.yml` 原本寫「GitHub cron 可能延遲幾分鐘」。**這句話是錯的。**

把這個 workflow 全部 136 次排程執行拿來統計（cron 設定自 2026-07-11 起未變）：

| | |
|---|---:|
| 誤差在 15 分鐘內 | **0 / 136（0%）** |
| 誤差在 1 小時內 | 約 21% |
| **延遲中位數** | **約 126 分鐘** |
| 最糟 | **747 分鐘（12 小時 27 分）** |

各時段中位延遲：06:30Z → 167 分、09:00Z → 126 分、10:00Z → 115 分。

而且**在惡化**：2026-08-27 之前平均約 1.4 小時；08-27、08-28 三次全部延遲 10～12.5 小時,
等於「台灣 14:30」的掃描在**隔天凌晨一點多**才發布。9 月的中位數約 4.5 小時。

**請以 12 小時的失敗情境來規劃,不是 2 小時。**

### 為什麼「多加幾個 cron 時間點」沒用

這是最直覺的做法,但實測否決了它：**44 個完整三次執行的日子裡,44 天的三個時間點都是
整批一起滑動**（同一天內的落差中位數 47 分、最大 78 分）。

延遲發生在 GitHub **建立執行**的階段,不是排隊等機器。整天一起延後,所以加第四個時間點
只會多一次遲到的執行。

（也不能在 job 裡 sleep 等到正確時間 —— job 上限 6 小時,而最糟延遲是 12.45 小時。）

## 二、解法

### 已採用（2026-09-14）：GitHub 內部的 scan-timer,不需電腦、不需外部帳號

`.github/workflows/scan-timer.yml` + `.github/scripts/scan_timer.sh`：

- cron 故意設很早（台灣 06:00、10:00）。它照樣會遲到,但**只要在 15:00 前到就好**。
- 到了之後 job 自己 `sleep` 到 15:00,再 `gh workflow run scan.yml`。
  實測 2026-09-14：dispatch 的 `created_at` 就是送出指令的那一秒,約 3 分鐘跑完。
- 超過 job 6 小時上限的等待,由腳本重新 dispatch 自己接力（`GITHUB_TOKEN` 可觸發 workflow_dispatch）。
- 「完成」的定義是 **Pages 上的 `meta.data_date` 等於今天且 `meta.list_status.state` 為 `final`**
  （2026-10-08 起；舊版 payload 沒有 `list_status` 時,退回原本的四個條件：
  `degraded` 為空、`checks` 不是 fail、指數資料是當日的）,不是「有跑完」。
  沒達成就每 75 分鐘重試,最晚 19:30（休市日最多空跑 4 次）。
- 首次在 15:00 而非 14:35：給 TPEX 發布留餘裕,避免上櫃快照不完整。
- 若兩個 cron 都遲到超過 15:00,仍會立刻補跑一次；再不行就退回 scan.yml 自己的晚到 cron。
- 手機「研究」頁有「立即更新」按鈕：手機上沒存金鑰時,只會開 GitHub 的 Run workflow 頁面（用瀏覽器裡已登入的 GitHub,不需要金鑰）；
  若在手機上設定了一把只有 Actions 權限的金鑰（只存在手機）,按鈕會直接觸發 scan.yml,但不帶 force_rescan。

### 每個交易日的清單只定稿一次（2026-10-08,`scanner/list_freeze.py`）

以前同一個交易日會被掃好幾次：15:00 的 scan-timer 一次,之後三個晚到 2～12 小時的 cron
各再掃一次,每次都重新排名、重新發布。同分的股票互換名次、遲滯（hysteresis）疊在當天自己的
結果上,15:05 看到的清單到 21:48 已經不一樣 —— 而用的是**同一天的收盤資料**。現在的規則
（`final-once-v1`）：

- **定稿條件**：發布的 payload 同時滿足以下各項才算 `final`,否則是 `provisional`（暫定）：
  資料日等於交易日、沒有資料源異常（degraded）、欄位自檢不是 fail（warn 可以）、
  大盤指數讀得到且是當日的、清單不是零檔（零檔一律暫定,見下）、掃描時間不早於 **15:00**
  （`FINAL_NOT_BEFORE`,必須等於 `scan_timer.sh` 的 `FIRST_ATTEMPT`）。
  結果寫在 `meta.list_status`（state / reasons / revision / first_published_at…）,
  並在 `data/signal_ledger.db` 的 `list_sessions` 表記一筆定稿標記,隨每日 state commit 進 repo。
- **定稿後的晚到 cron 一律不動**：同一交易日再跑時,在寫入任何東西之前就停下,
  **exit 3**（Actions 顯示 notice「list for this session is already final」,不是錯誤）：
  不重掃、不改 held_ids、不寫 picks、不建推薦、不重新部署 Pages,手機上的掃描時間也不會在半夜變動。
  （`tools/check_scan_result.py --strict` 也用 3,意思是「自檢 fail」,兩者無關;workflow 沒有用 `--strict`。）
- **暫定的發布會被重試**：degraded、自檢 fail、資料落後（颱風假／休市）、指數未更新、
  15:00 前的手動執行……這些都只是 `provisional`,timer 與晚到的 cron 照常重掃,
  第一個合格的執行才定稿。
- **唯一會在定稿後改變的：處置／注意股資訊**。交易所約 23:30 才公布處置與注意名單
  （D 日公告、D+1 生效）,15:00 的清單看不到。晚到的 cron 被凍結時會重抓一次,
  若已發布清單的限制欄位（`Trade_Restriction`、處置期間、撮合分鐘、預收款…）因此改變,
  就只改這些欄位與 `meta.quality.restrictions`,`revision` +1、`revised_reason` 記為
  `restriction_info`,重跑自檢後 **exit 4** 重新部署。絕不增刪或重排任何一檔,
  也不改 Buy_Ready／Buy_Block —— 唯一例外是新的限制種類屬於會擋買進的那一組
  （預設只有「暫停交易」）,此時該檔只能由可買變成不可買（`restricted`）,
  當天建立的推薦標為 superseded（`retracted:restricted`）。抓不到 Pages 或名單抓不完整時什麼都不做（exit 3）。
- **強制重建（給本人用）**：GitHub → Actions → daily-scan → Run workflow,
  勾選 **force_rescan** 再執行。重建後 `revision` +1、`revised_reason` 為 `force_rescan`;
  遲滯從前一個交易日的持有集合重新起算,不會疊在被取代的清單上。
  手機上的「立即更新」沒有金鑰時只會開這個 Actions 頁面；有金鑰時直接觸發 scan.yml,但**不帶** force_rescan,
  所以強制重建一定要從 Actions 頁面勾選。scan-timer 永遠不會強制重建。
- **自動修復**：帳本說已定稿、但 Pages 上不是（部署失敗）時,下一次執行會重新發布
  （`revised_reason` 為 `pages_behind`）。反過來 Pages 已定稿、帳本卻沒有標記
  （state commit 在 rebase 衝突時被丟掉）時,維持凍結並在 Actions 留下 warning,請本人留意。
  Pages 雖已定稿、但 `revision` 比帳本舊（例如 force_rescan 的部署失敗）也算「Pages 落後」,
  同樣重新發布;只有帳本那一版是 `restriction_info` 時不重掃,交給晚間補充從 Pages 那一版重新補上。
- **掃不出任何資料日期時不覆蓋**：若這次掃描連一檔都沒驗證到（結果與驗證結果都沒有 bar 日期）,
  判斷時視為「最新一個已定稿的交易日」,因此在程式不知道的休市日不會用一份空清單蓋掉已定稿的清單,
  也不會把持有集合清空。零檔的清單本身一律是 `provisional`（沒有資料日,永遠不會定稿）,
  後面的執行會再掃一次——寧可多掃,也不把一次失敗的空結果凍結一整天。
- **本機執行**：本機沒有 `PAGES_URL`,只看帳本。`git pull` 下來的 `signal_ledger.db`
  若已記下當天定稿,本機 `python scan_headless.py` 會直接 exit 3、什麼都不寫;
  要在本機重建請先設環境變數 `YENTOOL_FORCE_RESCAN=1`。本機帳本與狀態不會被 CI 讀到。
- **桌面 GUI**（`gui/scan_worker.py`）不經過定稿閘門,也不寫 `list_sessions`、不產生定稿標記
  （匯出的 `list_status` 停在 `provisional`/`unchecked`,不會部署）;但遲滯狀態與 picks
  也改用「資料所屬的交易日」：同一交易日在桌面重掃,起點與雲端相同,半夜重掃也不會記到隔天。
  修改掃描程式後 GUI 必須重開。

### 備選：外部排程器呼叫 workflow_dispatch

若 scan-timer 的 06:00/10:00 cron 常常遲到超過 15:00,再改用下面的外部觸發。

### 為什麼用 `workflow_dispatch` 而不是 `repository_dispatch`

**這是資安考量,不是延遲考量。**

- `workflow_dispatch` 只需要 **Actions: write**
- `repository_dispatch` 需要 **Contents: write**

`mobile/app.js` 就是 GitHub Pages 送到你手機上的檔案。**一個能改寫 repo 內容的 token,
就是一個能發布「讀取你 IndexedDB 持倉帳本」程式碼的 token。** 這個差別本身就足以決定選哪個。

### 設定步驟（需要你本人操作）

> 我不能代你建立帳號或處理 token —— 這些必須由你自己在自己的介面完成。

**步驟 1：建立 token**
前往 `github.com/settings/personal-access-tokens/new`

- Resource owner：你的帳號
- Repository access：**Only select repositories → `yentool`**
- Repository permissions：**Actions → Read and write**。**其他一律不要給。**
  （`Metadata: Read-only` 會自動附帶,無法取消）
- Expiration：選最長的,並在到期前一週設個提醒 ——
  **過期的 token 看起來就跟「掃描又遲到了」一模一樣**,正是你想擺脫的那種失敗模式
- Token 只會顯示一次。**它絕對不進 repo、不進 workflow 檔、不進任何 `mobile/` 底下的東西。**

**步驟 2：建立觸發器**（cron-job.org,免費,不需信用卡）

| 欄位 | 值 |
|---|---|
| URL | `https://api.github.com/repos/luke820001/yentool/actions/workflows/scan.yml/dispatches` |
| Method | `POST` |
| Header | `Authorization: Bearer <你的 token>` |
| Header | `Accept: application/vnd.github+json` |
| Header | `X-GitHub-Api-Version: 2022-11-28` |
| Header | `User-Agent: yentool-cron`（GitHub 會拒絕沒有 UA 的請求） |
| Body | `{"ref":"main"}` |
| 預期回應 | **204 No Content** |
| 時區 | `Asia/Taipei` |
| 時間 | 週一至週五 **14:35** 與 **17:05** |

記得開啟失敗通知信。免費方案每小時可執行 60 次,兩三個工作綽綽有餘。

**步驟 3：連續驗證三天。** 每次觸發後確認 Actions 在約 1 分鐘內出現執行,並檢查：

```bash
curl -sI https://luke820001.github.io/yentool/quotes.json | grep -i last-modified
```

### 誠實的但書

「dispatch 一定即時」是**推論,不是實測驗證過的**。常被引用的證據
（dispatch 執行的 `created_at == run_started_at`）證明不了什麼 —— 因為那 136 次排程執行
**全部**也都成立,包括延遲 747 分鐘那次。延遲發生在 GitHub 建立執行,不在 job 排隊。

GitHub 官方文件確實說 `schedule` 事件會被降級處理、可能延遲或丟棄,而 dispatch 不會。
**但請先觀察一週再信任它。**

### 準時能換到什麼

實測 151 次成功執行：管線耗時中位數 **2.83 分**、p90 3.57 分、最大 12.38 分。
Pages 部署再加約 12～20 秒。

> **觸發後約 3～4 分鐘,資料就會出現在手機上。**

Pages 的 CDN 不是延遲來源 —— 部署時會清 Fastly 快取,邊緣節點的 `Age` 與部署時間差在一秒內。

**AI 報告的重試上限（2026-10-08,plan P1-7）**：Pages 要等整個「Run scan」步驟（含 AI 報告）
結束才上傳,所以 AI 的時間就是手機資料的等待時間。`gemini_hook/gemini_client.py`：
503／逾時／連線中斷只重試一次（等 15 秒,Retry-After 最多 30 秒）,429 維持 10→20 秒；
同一次掃描三份報告（上櫃先做）**共用一個 90 秒的重試額度**（`RETRY_BUDGET_S`）,
額度不夠就不重試、直接用模板。所以重試最多讓發布晚約 90 秒。
用了模板時 `meta.report_sources[市場].source == "template"`,檢測只記 info `report_template`,
不會讓 scan-timer 重跑。

⚠ 在把觸發時間提早到 14:35 之前,請先確認掃描**實際使用的**來源何時發布資料：
`ingestion/price_volume_multi.py` 用的是 `www.twse.com.tw/exchangeReport/STOCK_DAY` 與
`www.tpex.org.tw/www/zh-tw/afterTrading/tradingStock`。
**不要**用 `openapi.twse.com.tw` 那一組來推論 —— 它是隔夜才發布前一個交易日的資料
（2026-09-10 晚上 22:50 時,它的第一筆仍是 `1150909`),而掃描根本沒用到它。
**準時但在資料還沒出來之前跑,是製造新 bug,不是修好舊 bug。**

## 三、盤中即時行情：能做到什麼、不能做到什麼

### 結論：目前架構下做不到「價格不斷跳動」

有三道牆,任何一道都足以否決:

**(a) 整條管線根本沒有盤中資料來源。**
`ingestion/` 底下每一個端點都是盤後（EOD）。搜尋 `mis.twse`、`getStockInfo`、`realtime`、
`intraday` 全部沒有結果。**在 11:00 觸發掃描,得到的是昨天的收盤價,不是即時價。**
所以「盤中多觸發幾次」這個最直覺的想法,買到的是**零**。

**(b) 手機不能直接抓行情來源（CORS）。**
用 `Origin: https://luke820001.github.io` 實測：

| 端點 | 結果 |
|---|---|
| `mis.twse.com.tw/.../getStockInfo.jsp` | 200 有真實資料,但**完全沒有 `Access-Control-*` 標頭** |
| `openapi.twse.com.tw/v1/...` | 200,無 CORS |
| `www.tpex.org.tw/openapi/v1/...` | 200,無 CORS |
| Yahoo `query1/v8/finance/chart/2330.TW` | 200 有 271 根一分鐘 K,**無 CORS**；query2 首次就 429 |
| FinMind | CORS 開放,但盤中資料集 `taiwan_stock_tick_snapshot` 回 422,是**被鎖**不是額度問題 |

MIS 也不吃 JSONP（`callback=` 與 `_callback=` 都被忽略),所以**沒有任何純前端的繞法**。
除了 Fugle 以外全部需要 proxy —— 也就是你不想要的伺服器。

**(c) 就算做了 proxy,也沒有全市場的盤中來源可抓。**
TWSE OpenAPI 143 個路徑裡沒有任何個股盤中報價；唯一標「每5秒」的 `MI_5MINS` 是全市場彙總。
TPEx 225 個路徑裡,`tpex_mainboard_quotes` 看起來像報價（有 `LatestBidPrice`),
但 TPEx 自己標的是**上櫃股票收盤行情**,`Last-Modified` 在台灣時間 22:00,收盤後 8.5 小時。

而唯一真正的盤中來源 `mis.twse.com.tw` 是未公開文件的端點,且 TWSE 使用條款第 6 條禁止用
「自動化裝置、指令碼、自動程式、蜘蛛程式、爬蟲程式或擷取程式」擷取資料。
TWSE 的即時行情轉發授權是商業銷售,起價每月 **10 萬元**。

### 唯一可行的盤中選項：Fugle 富果免費方案

**實測驗證**：對 `api.fugle.tw` 送出 `Origin: https://luke820001.github.io` 的 CORS preflight,
回應 204 並帶 `Access-Control-Allow-Origin: https://luke820001.github.io` —— **瀏覽器可以直接讀**。

| | |
|---|---|
| 費用 | NT$0,只需註冊富果會員（不需要券商帳戶） |
| 延遲 | 交易所即時,非延遲行情 |
| 更新頻率 | REST 每分鐘 60 次 → 持有 N 檔可各約每 N 秒更新一次 |
| WebSocket | 免費僅 5 個訂閱 / 1 條連線 |

**但有三個真實代價,你必須知道再決定：**

1. **免費方案不含「盤中快照」**,所以只能報你持有的那幾檔,**無法盤中重掃 1,900 檔宇宙**。
2. **使用條款**禁止「轉接交易資訊」。用你自己的 key、在你自己的裝置上是個人使用,沒問題 ——
   但**把 key 放進公開的 github.io 程式包裡,等於任何訪客都能用你的 key 取行情**,
   那個「轉接」的解釋我不會想去辯護。所以 key 必須由你在 App 裡輸入、存在 IndexedDB,
   **和持倉一樣留在裝置上**,絕不進 repo。
3. **這會犧牲一個目前刻意保護的隱私性質。** `quotes.json` 之所以發布**全市場**,
   就是為了讓「出現在檔案裡」不透露任何持股資訊。
   **若改成只向 Fugle 查詢你持有的股票,等於把一份精確、有時間戳的持股清單交給 Fugle。**
   這是威脅模型的實質改變,應該由你知情後決定,不該由我默默做掉。

### 附帶發現：一個瀏覽器可直接讀的盤後來源

`www.twse.com.tw/rwd/*` 回傳 `Access-Control-Allow-Origin: *`,
其中 `MI_INDEX?type=ALLBUT0999` 一次涵蓋整個上市市場。

它是**盤後**資料,解決不了盤中問題 —— 但它免費、免 token、涵蓋全市場,
如果之後想讓手機自己偵測「`quotes.json` 是不是過期了」,這是不需要任何廠商的做法。
